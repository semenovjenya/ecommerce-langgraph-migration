# Оптимизация агентского runtime

## 1. Компактная передача evidence

В типовых ответах SQL/API повторяются названия полей, источник, валюта, период и provenance. `marketing.compact.pack` преобразует однородный массив объектов в `columns`, `shared`, `rows`:

```json
{
  "columns": ["sku", "orders"],
  "shared": {"currency": "RUB"},
  "rows": [["DEMO-A", 0], ["DEMO-B", null]]
}
```

После `unpack` восстановятся исходные объекты с валютой в каждой строке. `null` не превращается в ноль, `false` не превращается в число, исходные данные не меняются. Неоднородные списки сохраняют обычную форму. Зарезервированная структура не принимается молча: конфликт приводит к ошибке.

В `payload()` проверяется равенство канонического JSON после roundtrip. Лимит размера проверяется отдельно. Компактный view не заменяет полный checkpoint и не означает обрезку строк.

### Измерение

```bash
uv run --frozen python -m benchmarks.evidence_payload --output benchmarks/results.json
```

Скрипт использует реальную функцию из runtime и детерминированные синтетические данные. Сравниваются байты UTF-8 **одинаково канонизированного** JSON, а не pretty-printed baseline против minified результата.

| Набор | До, байт | После, байт | Снижение | Roundtrip |
| --- | ---: | ---: | ---: | --- |
| repeated_daily_rows | 147132 | 35276 | 76,02% | exact |
| nested_evidence | 51881 | 16930 | 67,37% | exact |
| heterogeneous_control | 38 | 38 | 0% | exact |

Результат не обещает такое же снижение на произвольных данных. Размер prompt, tokenizer, model reasoning и output tokens не измерены. Latency и стоимость требуют отдельных end-to-end замеров.

## 2. Ограниченный цикл исследования

В `marketing/research_model.py` модель получает явный оставшийся бюджет: до трёх решений, двух раундов и пяти уникальных проверок для соответствующего исследовательского режима. Валидаторы журнала в `research.py` проверяют version, identity и границы вызовов.

Это ограничение конкретного режима, а не универсальный предел всех subgraphs. Исторические версии журналов имеют отдельные контракты совместимости. Аварийный повтор незавершённого node не даёт exactly-once гарантии биллинга провайдера.

## 3. Повторное использование полученных результатов

Завершённые проверки исключаются из доступных повторных действий. Журнал хранит результаты с identity и scope, чтобы дальнейший review использовал уже собранное evidence. Это ограниченная повторная обработка в рамках workflow; глобальный межклиентский cache здесь не заявляется.

Ключи исследования учитывают владельца, операцию и версию источника. Данные разных SKU, периодов или tenants нельзя смешивать ради экономии вызовов.

## 4. Ссылки вместо бесконтрольных payload

`BusinessToolClient` проверяет типизированные ответы и artifact references. Крупный ответ можно получать адресно через reference, с повторной валидацией identity, размера, hash и scope. Конкретный backend должен предоставлять совместимый artifact endpoint.

Это уменьшает необходимость переносить один и тот же большой payload через каждый интерфейс. Само наличие reference не подтверждает, что данные доступны, актуальны или принадлежат вызывающему пользователю.

## 5. Checkpoint resume

LangGraph сохраняет границы выполнения, состояние и pending nodes. Пример `examples/checkpoint_demo.py` проверяет остановку перед `synthesis` и продолжение того же thread.

В демонстрации checkpoint хранится в памяти процесса. Durable restart recovery требует PostgreSQL и отдельных integration tests. Уже выполненные внешние side effects нельзя считать безопасными для повтора только потому, что у графа есть checkpoint: за idempotency, audit и read-after-write отвечает бизнес-ядро.

## Цена оптимизации

- Компактное представление сложнее читать; модель должна понимать схему.
- CPU-работа упаковки и проверка roundtrip не бесплатны; этот benchmark не измеряет скорость.
- Строгий бюджет иногда завершает исследование с `insufficient_data`.
- Reference требует доступного источника и согласованных TTL/ownership правил.
- Checkpoint schema и private journals требуют контроля совместимости при обновлении.
